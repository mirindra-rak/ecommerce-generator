## Étapes de développement

### Story 01 — Schema, types, repository

**1. Ajouter les enums et modèles Prisma**
Ajouter dans `schema.prisma` :

- Enum `TargetType` : `ALL`, `CATEGORY`, `PRODUCT`, `BRAND`
- Enum `DiscountType` : `PERCENTAGE`, `FIXED_AMOUNT`
- Modèle `CatalogPriceRule` : `id` (cuid), `name` (String), `active` (Boolean, défaut true), `startDate` (DateTime?), `endDate` (DateTime?), `priority` (Int, défaut 0), `targetType` (TargetType), `discountType` (DiscountType), `discountValue` (Int), `floorPrice` (Int?), `customerLabel` (String?), `showStrikethrough` (Boolean, défaut true), `createdAt`, `updatedAt`, `targets` (relation)
- Modèle `CatalogPriceRuleTarget` : `id` (cuid), `ruleId` (FK → CatalogPriceRule, onDelete Cascade), `targetId` (String), index composite sur `[ruleId, targetId]`
- Index composite sur `CatalogPriceRule` : `[active, startDate, endDate]` pour la requête de résolution

Test : `pnpm --filter @pharmacie/core db:migrate` passe, `db:generate` régénère le client.

**2. Créer les types TypeScript**
Fichier `promotion.types.ts` :

- `CreateCatalogPriceRuleInput` : input de création avec `targetIds: string[]` (au lieu de la relation Prisma)
- `UpdateCatalogPriceRuleInput` : Partial du create, avec `id` requis
- `ResolvedPrice` : `{ originalPriceExclTax, finalPriceExclTax, originalBreakdown: PriceBreakdown, finalBreakdown: PriceBreakdown, discount: DiscountDetail | null }`
- `DiscountDetail` : `{ type: DiscountType, value: number, amount: number, ruleId: string, customerLabel: string | null }`
- `ProductContext` : `{ productId: string, categoryIds: string[], brandId: string | null }` — contexte minimal pour évaluer les règles

Test : `pnpm type-check` passe.

**3. Créer le repository**
Fichier `promotion.repository.ts`, pattern identique à `brandRepository` / `categoryRepository` :

- `create(input: CreateCatalogPriceRuleInput)` — crée la règle + targets en transaction implicite (createMany nested)
- `findById(id: string)` — avec include targets
- `findMany()` — triées par priorité desc, avec targets
- `update(id: string, input: UpdateCatalogPriceRuleInput)` — upsert des targets (delete + recreate)
- `remove(id: string)` — cascade supprime les targets
- `findActiveForProduct(productId, categoryIds, brandId)` — WHERE active=true AND dates valides AND (targetType=ALL OR targetId IN (productId, categoryIds, brandId)), ORDER BY priority DESC, LIMIT 1
- `findActiveForProducts(contexts: ProductContext[])` — version batch : une seule requête, retourne toutes les règles actives qui matchent au moins un des produits, triées par priorité desc

Test : tests d'intégration avec base de test (pattern existant dans le projet).

### Story 02 — Service de résolution

**6. Créer le service de résolution**
Fichier `promotion.service.ts` :

- `resolvePrice(variant: { priceExclTax: number }, taxRate: TaxRateSnapshot, rules: CatalogPriceRule[])` — pure function :
  1. Filtre les règles valides (dates)
  2. Prend la première (déjà triée par priorité desc)
  3. Calcule la réduction selon le type (% : `Math.round(price * bps / 10000)`, fixe : valeur directe)
  4. Applique le prix plancher (`Math.max(finalPrice, floorPrice)`)
  5. Appelle `calculatePriceBreakdown(finalPriceExclTax, taxRate)` du module pricing
  6. Retourne `ResolvedPrice`
- Sans règle applicable → `ResolvedPrice` avec `discount: null` et `finalBreakdown === originalBreakdown`

Test : scénarios 1-6 de la story 02 en tests unitaires (données in-memory, pas de DB).

**7. Créer la résolution batch**
Même fichier, fonction `resolvePrices(products: Array<{ variants, taxRate, context: ProductContext }>, rules: CatalogPriceRule[])` :

- Reçoit les règles déjà chargées (le caller fait la requête DB via `findActiveForProducts`)
- Pour chaque produit, filtre les règles qui matchent son contexte
- Applique `resolvePrice` sur chaque variant
- Retourne une Map `productId → variant[] avec prix résolus`

Test : scénario 7 de la story 02 — 20 produits, 3 règles, résolution correcte.

**8. Tests d'intégration repository**
Fichier `promotion.repository.test.ts` :

- Vérifier le filtrage par dates (règle future ignorée, règle expirée ignorée)
- Vérifier l'ordre par priorité

Test : `pnpm test` passe.

## Points d'attention

- **Performance batch** : `findActiveForProducts` doit faire 1 seule requête SQL, pas N. La requête WHERE utilise `targetId IN (...)` avec la liste de tous les IDs (produits + catégories + marques) concaténés. Le filtrage fin (quelle règle pour quel produit) se fait en mémoire dans le service.
- **Arrondi monétaire** : les réductions pourcentage produisent des fractions → `Math.round` comme dans le pricing existant. Le prix plancher s'applique APRÈS l'arrondi.
- **Priorité en cas d'égalité** : si deux règles ont la même priorité, prendre la plus récente (`createdAt DESC` comme second critère de tri).
- 🚧 **Table de liaison vs JSON array** : la spec prévoit `CatalogPriceRuleTarget` (table de liaison). Alternative : stocker `targetIds` en colonne `String[]` (Prisma native array). La table de liaison est plus propre pour les requêtes (jointure vs ANY), on part sur la table de liaison.
- 🚧 **Règle targetType=ALL sans targets** : valider côté service que si `targetType=ALL`, `targetIds` est vide (et inversement). Erreur `MissingTargetIdsError` sinon.
